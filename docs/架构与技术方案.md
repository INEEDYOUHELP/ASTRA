# Astra 项目架构与技术方案

## 1. 目标与范围

本方案将 `测试题目.md` 的要求落为可开发、可测试、可演示的工程结构，重点覆盖：

- 合约边界与调用关系
- 资金分配与安全权限（含多签）
- 部署脚本与 Uniswap 集成
- 预言机与动态销毁机制
- 前端和链下服务最小实现路径

---

## 2. 总体架构分层

### 2.1 链上合约层

1. `AstraToken`：ERC20 固定总量代币与初始分配执行。
2. `AstraVesting`：团队/投资者多受益人归属释放。
3. `AstraStaking`：质押、赎回、奖励累计与领取、阈值锁定。
4. `AstraReferral`：首质押推荐绑定与 5% 一次性推荐奖励登记。
5. `AstraBurnController`：预言机触发后执行代币销毁策略。
6. `AstraTreasury`（可选）：生态基金/流动性拨备代理金库。

### 2.2 链下服务层

1. `Keeper/Job`：定时读取链下指标 + 链上 LP 状态，决定是否触发 `checkAndBurn()`。
2. `OracleAdapter`：将链下订单指标映射为链上可验证参数（可先做 mock）。
3. `Indexer`（可选）：监听事件构建前端展示数据。

### 2.3 应用层

1. 前端 dApp：钱包连接、质押、奖励领取、归属提取、推荐绑定。
2. 运维脚本：部署、初始化、角色分配、加池、验收脚本。

## 3. 合约职责与调用关系

## 3.1 `AstraToken`

- 基于 OpenZeppelin `ERC20` + `AccessControl`。
- 部署时一次性 mint 10 亿，按比例分配：
  - 40% 生态基金多签地址
  - 30% `AstraStaking`
  - 15% `AstraVesting`（团队额度）
  - 10% `AstraVesting`（投资者额度）
  - 5% 流动性拨备地址（建议多签或 `AstraTreasury`）
- 禁止后续随意 mint；若实现可销毁，限制为特定角色或控制器。

## 3.2 `AstraVesting`

- 支持多个受益人计划（team/investor）。
- 计划字段：
  - `beneficiary`
  - `totalAmount`
  - `start`
  - `cliffDuration`
  - `vestingDuration`
  - `released`
- `releasable = vested(now) - released`。
- 团队计划：部署时起算，6 个月 cliff + 24 个月线性。
- 投资者计划：可在资金入仓时设置 start，0 cliff + 18 个月线性。

## 3.3 `AstraStaking`

- 核心变量：
  - `totalStaked`
  - `rewardRatePerSec`
  - `accRewardPerShare`
  - `lastRewardTime`
  - `lockTriggered`
  - `minRewardReserve = 3_000_000e18`
- 用户变量：
  - `amount`
  - `rewardDebt`
  - `pendingManual`（可选）
- 操作：
  - `stake(amount, referrer?)`
  - `unstake(amount)`
  - `claimReward()`
  - `emergencyWithdraw()`（可选）
- 奖励逻辑用典型 `accRewardPerShare` 模型，避免 O(n)。
- 每次状态更新检查余额阈值，触发 `lockTriggered=true` 后停止新增奖励累计。

## 3.4 `AstraReferral`

- 维护 `referrerOf[user]`，仅首质押绑定一次，禁止自推荐。
- `onFirstStake(user, amount, referrer)` 由 `AstraStaking` 调用。
- 记录推荐奖励 `reward = amount * 5%` 为可领取额度。
- 推荐奖励资金来自社区池（建议在 `AstraStaking` 中统一出账）。

## 3.5 `AstraBurnController`

- 接收 keeper/预言机输入，检查规则是否满足。
- 满足条件时调用 token 的 `burn` 或从指定池地址执行受控销毁。
- 记录周期状态，防止同一时间窗重复触发。

---

## 4. 关键时序与资金流

1. 部署阶段：部署全部合约 -> 执行初始分配 -> 配置角色。
2. 质押阶段：用户 `approve` -> `stake` -> 累计奖励份额。
3. 推荐阶段：首次 `stake` 时写入推荐人并记账推荐奖励。
4. 锁仓阶段：受益人按计划周期 `release()` 提取已释放代币。
5. 流动性阶段：部署脚本从流动性拨备地址注入 Uniswap。
6. 平衡阶段：keeper 周期触发 `checkAndBurn`，执行动态调节。

## 5. 多签钱包设计与落地

建议使用 Safe（原 Gnosis Safe）作为测试网多签钱包。

## 5.1 多签实例建议

1. `EcoFundSafe`（生态基金）
2. `LiquiditySafe`（流动性拨备）
3. `AdminSafe`（协议管理角色持有方，可选）

## 5.2 签名门限建议

- 开发/测试期：`2/3`
- 准生产/主网：`3/5` 或更高

## 5.3 权限分配原则

- `DEFAULT_ADMIN_ROLE` 不给 EOA，给 `AdminSafe`。
- 关键角色拆分：
  - `PARAM_SETTER_ROLE`：可调奖励速率上限内参数
  - `PAUSER_ROLE`：紧急暂停（如实现）
  - `KEEPER_ROLE`：调用预言机检查函数
  - `TREASURY_ROLE`：流动性资金执行
- 尽量让角色分离，避免单角色覆盖全部高危操作。

## 5.4 Safe 操作流程（简版）

1. 创建 Safe 并设置 owner 与阈值。
2. 部署合约时将关键地址参数填入 Safe 地址。
3. 用部署脚本调用 `grantRole(role, safeAddress)`。
4. 由 Safe 发起和批准后续管理交易（参数更新、加池、资金移动）。

## 6. 技术实现建议

## 6.1 合约开发

- Solidity `^0.8.24`
- OpenZeppelin：
  - `ERC20`
  - `AccessControl`
  - `ReentrancyGuard`
  - `SafeERC20`
  - `Pausable`（可选）

## 6.2 开发框架

- 推荐 Foundry（测试快、Fuzz 友好）
- 可搭配 Hardhat 脚本/前端交互（ethers/viem）

## 6.3 前端

- Next.js + TypeScript
- `wagmi` + `viem`
- 页面模块：
  - Stake/Unstake/Claim
  - Vesting 可领取查询与提取
  - Referral 奖励领取
  - 协议状态（奖励池余额、阈值状态、当前 APR）

## 6.4 链下任务

- 定时任务（cron）每 N 分钟：
  - 拉取链下订单 mock 数据
  - 读取 Uniswap LP 状态（储备、价格）
  - 调用 `AstraBurnController.checkAndBurn(...)`

## 7. 动态销毁机制（建议可实现版本）

可先定义一个清晰、可测试的规则：

1. 时间窗：每 7 天一个周期。
2. 判定输入：
  - `netLiquidityAddedETH`（周期内新增 LP 的 ETH 净值）
  - `priceDeviationBps`（ASTRA/ETH 价格偏离）
3. 触发条件：
  - `netLiquidityAddedETH < MIN_ADDED_ETH` 且 `priceDeviationBps > MAX_DEVIATION_BPS`
4. 销毁量：
  - `burnAmount = min(maxBurnPerEpoch, rewardPoolBalance * burnBps / 10_000)`
5. 防误触发：
  - 每周期最多触发一次
  - keeper 调用需签名角色校验

## 8. 测试策略（必须先写）

1. 单元测试
   - ERC20 初始分配精确性
   - Vesting 释放曲线
   - Staking 奖励累计与领取
2. 场景测试
   - 多用户错峰质押/赎回
   - 首质押绑定推荐与奖励领取
   - 奖励池跌破 1% 后行为验证
3. 安全测试
   - 重入与权限绕过
   - 参数越界与重复领取
4. 不变量/模糊测试
   - 累计发放不超预算
   - `totalStaked` 与用户总额一致
